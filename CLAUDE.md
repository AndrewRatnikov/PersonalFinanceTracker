# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm run dev        # start dev server on port 3000
npm run build      # production build
npm run preview    # preview production build locally
npm run test       # run all tests (Vitest)
npm run test:precache  # build, then check sw.js precaches the whole build output
npm run lint       # ESLint
npm run check      # prettier --write + eslint --fix
```

Tests use Vitest + jsdom (`vitest.config.ts`, separate from `vite.config.ts`) and live next to the module they test; route tests live in `src/test/routes/`. SQL tests run the Supabase migration in PGlite (`@electric-sql/pglite`, dev dependency) through the harness in `src/test/sql/harness.ts` (a Supabase stand-in: `auth.users`, `auth.uid()`, the `anon` / `authenticated` roles and Supabase's default privileges); every SQL / PGlite test file starts with `// @vitest-environment node`. See `.claude/rules/testing.md`.

## Architecture

**Framework:** TanStack Start (React 19 + TanStack Router file-based routing + Vite + Nitro/Vercel SSR). Routes live in `src/routes/`; the route tree is auto-generated into `src/routeTree.gen.ts` — do not edit it manually (when the generator can't run, mirror an existing route's entries exactly; `vite build` regenerates it). `@/` is an alias for `src/`.

**UI:** Tailwind CSS v4 + shadcn/ui components (in `src/components/ui/`). `components.json` controls shadcn config. Charts use Recharts. Theme variables in `src/styles.css` hold full oklch colours, so use `var(--token)` in inline styles and chart props, never `hsl(var(--token))`.

### Storage — local-first, encrypted IndexedDB

The app migrated away from Supabase for data. **Supabase is used only for the optional account** (see Unlock gate). All data lives in IndexedDB, encrypted at rest.

The primary data module is `src/lib/localDb.ts`:

- A module-level `let _key: CryptoKey | null = null` holds the vault DEK (a non-extractable AES-GCM key, set by `vault.ts` via `unlockLocalDb`) in memory only — never persisted. `getLocalDbKey()` returns it; `getLocalStore()` returns the shared `minima-local`/`data` store handle that `vault.ts` also uses.
- Every record (expense, income, category, budget) carries `updatedAt` (ISO), set on create and update.
- `readStore` silently returns `undefined` when `_key` is null; `writeKeysMany` (every write goes through it, one `setMany`) throws `"LocalDb not initialized"`.
- **Expense storage is chunked by month** (`expenses_YYYY_MM`). `categories` (expense categories), `incomeCategories`, `income`, `budgets`, `recurring` and `syncedSettings` (one encrypted record, not an array) are single IDB keys. All of them are data keys (`SINGLE_KEY_LABELS` in `dataErrors.ts`), so `hasLocalData`, migration, quarantine, backup and wipe cover them.
- **isLive rule (tombstones):** every record type may carry `deletedAt?: string`. A delete (`deleteExpense`, `deleteIncome`, `deleteCategory`, `deleteIncomeCategory`, `deleteBudget`, `deleteRecurring`) keeps the record in its array (an expense in its chunk) with `deletedAt = updatedAt = now`; deleting a missing or already deleted record writes and announces nothing. **Every reader and computation filters with `isLive(record)`** (`src/lib/syncRecords.ts`): `getAll*`, `getExpensesForRange`, the category joins, totals, analytics, the dashboard summary, recurring processing and upcoming, conversion, CSV export, suggestions, repeat-last, CSV import fingerprints and the category name uniqueness checks (a deleted name can be reused; it gets a new id). Mutations treat a tombstone like a missing record. The delete refusals count live records only. `deleteCategory` also tombstones the live budgets of the category. `undeleteExpense(id, createdAt)` clears `deletedAt` and bumps `updatedAt` + `rev`. Data is really removed only by `quarantineKey`, `clearLocalDb` / wipe and `compactTombstones(olderThan)` (removes tombstones whose `deletedAt` is strictly older; the sync engine calls it after a cycle with `maxRev`). `readEntriesForConversion` stays raw; its callers filter.
- **rev rule (`meta:sync`):** the plaintext `meta:sync` key holds `{ localRev }` (missing or junk = 0; `getLocalRev()` works before unlock). Every user write adds `SYNC_META_KEY` to its lock, stamps `rev = ++localRev` on each record it creates, changes, deletes or undeletes, and writes the data keys **and** `meta:sync` in the same `setMany`, so a failed transaction leaves both byte-identical. **A write that sets `updatedAt` stamps `rev`, and only such writes do** (this includes `convertBudgets`' converted budgets and the settings record). Derived writes (`applyEntryConversions`, quarantine, `migrateSyncedSettings`, the legacy income rewrite of `ensureIncomeCategories`, the vault v1 migration, `applyIncomingRecords`, `compactTombstones`) neither read nor advance `meta:sync`. `rev` never leaves `localDb`: no public read or return value carries it, and backups / CSV / sync records strip it.
- **Deterministic occurrence ids:** a record generated for a recurring occurrence (`processDueRecurring`, `addRecurring` with `createThroughToday`, `confirmRecurringOccurrence`, today's record of `addRepeatingExpense` / `addRepeatingIncome`) gets `occurrenceRecordId(recurringId, occurrenceDate)` (`src/lib/occurrenceId.ts`: SHA-256 of `${recurringId}:${occurrenceDate}`, first 16 bytes as a version-5-style UUID), so two devices produce the same id. The `recurringId` + `occurrenceDate` check stays, includes tombstones (a deleted generated record is never regenerated) and also skips a date whose computed id already exists. Older records keep their random ids.
- **Sync API (used by the sync engine):** `listChangedRecords(sinceRev)` → `{ maxRev, records: SyncRecord[] }` (every record, tombstones included, with `sinceRev < rev <= maxRev`; no rev = 0, so `-1` is the full snapshot; `data` without `rev` / `conversion` / `category`). `applyIncomingRecords(records)` validates the whole batch first, then per record uses `mergeRecord` (newer `updatedAt` wins; an equal time with different content is a `conflict-same-time`, resolved by `sameTimeWinner`: the tombstone, else the larger canonical JSON), moves expenses to the chunk of their `createdAt`, stores tombstones as tombstones, writes one `setMany` without `meta:sync` or rev, and runs `afterCommit`; returns `{ applied, kept, conflicts }`. Backup merge uses the same `mergeRecord`.
- **Settings classification:**

  | Kind | Where | Fields |
  | ---- | ----- | ------ |
  | Synced | encrypted `syncedSettings` record (`{ id: 'settings', mainCurrency, fetchExchangeRates, updatedAt, rev }`) | `mainCurrency`, `fetchExchangeRates` |
  | Per device | plaintext `meta:settings` | `failedUnlockAttempts`, `unlockBlockedUntil`, `autoLockMinutes`, `installHintDismissed`, `persistRequestedAt`, `recoveryKeyConfirmed`, `backupReminderDays`, `lastBackupAt`, `backupReminderSnoozedUntil`, `lastDataChangeAt` |
  | Per device | localStorage + cookie | `minima_lang` |
  | Local bookkeeping | plaintext `meta:sync` | `localRev`, plus the sync engine's fields (`enabled`, `userId`, `vaultId`, `deviceId`, `pushedRev`, `pullCursor`, `headerRev`, `lastSyncAt`, `lastError`, `headerPending`; see Sync engine) |

  `readSyncedSettings()` reads the record (a `DecryptError` propagates), else the legacy plaintext fields, else the defaults (`UAH`, `true`, `updatedAt` 1970-01-01). `migrateSyncedSettings()` runs first in `prepareUnlockedVault`: when the record is absent it is created from the legacy fields (no rev; `updatedAt` = now when a valid legacy value existed, else the epoch) and the legacy fields leave `meta:settings`, in one `setMany` (idempotent; an unreadable record counts as present). `updateSyncedSettings` / `convertBudgets` write the record with a rev and also strip leftover legacy fields. Before unlock nothing needs the main currency.
- **Income categories:** `incomeCategories` holds `Array<Category>` managed like the expense categories (`getAllIncomeCategories`, `addIncomeCategory`, `updateIncomeCategory`, `deleteIncomeCategory`; names trimmed and unique ignoring case; the add/update share a helper parameterised by storage key with `addCategory`/`updateCategory`). `deleteIncomeCategory` locks `income` + `incomeCategories` and refuses while entries use it ("N income entries use this category"). `IncomeEntry` has `categoryId`; the free-text `source?` is legacy, kept only for reading and conversion. `getAllIncome()` / `addIncome()` join `category` (never stored). `ensureIncomeCategories()` (idempotent, locks `income` + `incomeCategories`) does nothing when the `incomeCategories` key exists; otherwise it converts legacy sources with the pure `convertIncomeSources` (`src/lib/incomeCategories.ts`: distinct trimmed sources ignoring case, first spelling wins; missing defaults Salary/Freelance/Gifts/Investments/Refunds/Other; empty source → Other) and writes both keys in one `setMany`. `prepareUnlockedVault({ isNewVault, lang })` runs after every unlock: expense defaults (in `lang`, the UI language) for a new vault, then `ensureIncomeCategories(lang)`, then `processDueRecurring()`; it returns `{ recurringCreated }`.
- **Category default currency:** expense and income categories may carry `defaultCurrency?: Currency` (additive; absent = the main currency). `updateCategory` / `updateIncomeCategory` take `defaultCurrency?: Currency | null`: `undefined` keeps the stored value (so a rename keeps it), `null` deletes the key (never stored as `null`), an unknown value rejects with "Invalid currency" and writes nothing. Forms read it only through `currencyForCategory(category, mainCurrency)` (`src/lib/categoryCurrency.ts`, which ignores junk from a restored backup), and only for new entries: edit mode and a currency given in `initial` / the URL count as an explicit choice, and a currency the user tapped is never overridden. Settings → Categories: a native "Currency" select per row (`category-default-currency-<id>`, "Main currency" = clear). Backups round-trip it as part of the raw record; `categories.csv` stays `name,icon`.
- **Recurring** (spec §14): `recurring` holds `Array<RecurringItem>`; the pure schedule maths (date-only, month-end clamping from `startDate`, totals, labels, `markOccurrenceHandled`) is in `src/lib/recurrence.ts`. Generated records carry `recurringId` + `occurrenceDate`, the idempotency key: an occurrence whose target already has that pair is never created again (`updateExpense` keeps both fields). `processDueRecurring(today?)` handles one active auto item at a time: target keys planned outside the lock, then re-read under `withWriteLock(['recurring', ...chunks or 'income'])` and written in ONE `setMany` (`writeKeysMany` mixes single keys and chunks); an item whose category is gone is skipped and stays pending. It runs from `prepareUnlockedVault` and from `RecurringScheduler` in `__root.tsx` (tab visible, local date change; toast "Added N recurring transactions"). Ask mode: `getDueRecurring`, `confirmRecurringOccurrence` (optional amount/description override), `skipRecurringOccurrence`. CRUD: `getAllRecurring`, `addRecurring(input, { createThroughToday })`, `updateRecurring` (future only; progress fields kept), `setRecurringPaused` (resume skips the paused period), `deleteRecurring` (a tombstone; the records it created are kept). Quick Add / Add Income repeat: `addRepeatingExpense` / `addRepeatingIncome`. `deleteCategory` / `deleteIncomeCategory` also lock `recurring` and refuse with "Used by N recurring items". A sync message for `recurring` invalidates `['recurring']`, `['expenses']`, `['income']` and `['analytics']`.
- **Write lock:** every mutation runs its whole read-modify-write inside `withWriteLock(keys, fn)` from `src/lib/writeLock.ts`, locking the storage key(s) it touches (e.g. `updateExpense` locks the old and new chunk, `deleteCategory` locks `budgets` + `categories` + `recurring`). It uses `navigator.locks` (`minima:<key>`, cross-tab) when available and an in-memory per-key FIFO queue otherwise; multiple keys are acquired in sorted order. The lock is **not re-entrant**: never call another locked mutation from inside a locked section. Imports call the mutations row by row and so inherit the lock.
- **DecryptError** (`src/lib/dataErrors.ts`, re-exported from `localDb.ts`) carries the `storageKey`. Reads (`readStore` / `readChunk`) throw it for a blob that can't be decrypted; **mutations never catch it**, so an undecryptable blob is never overwritten. The global `QueryCache` / `MutationCache` `onError` (`src/lib/queryClient.ts`) reports it to `src/lib/dataProblem.ts`, and `DataProblemGate` (plus an error boundary) in `__root.tsx` replaces the routes with the Data problem screen (Retry, or Quarantine and continue).
- **Quarantine keys:** `quarantineKey(key)` moves the raw blob unchanged to `quarantine:<key>:<ISO timestamp>`, and only then deletes the original. `quarantine:*` keys are ignored by `allExpenseChunkKeys()` and every reader; `hasLocalData()` ignores them too.
- **lastDataChangeAt:** after every committed mutation (all of them except `quarantineKey`, `migrateSyncedSettings`, `compactTombstones` and the converter's own background writes: `applyEntryConversions` and `convertBudgets` without `setMainCurrency`) `localDb` merges `lastDataChangeAt` (ISO) into the plaintext `meta:settings` object, under the `meta:settings` write lock, before the mutation's promise resolves. A failed marker write is logged and never fails the mutation. `expenseChunkKey(date)` is exported (UTC month chunk key).
- **Multi-tab sync:** after each committed write `localDb` posts `{ type: 'changed', keys }` on `BroadcastChannel('minima')` (`src/lib/syncChannel.ts`); `__root.tsx` calls `listenForChanges(queryClient)` so other tabs invalidate the matching React Query keys. Without `BroadcastChannel` this is a no-op.
- **Main currency** (spec §15): expenses and income keep their typed `amount` / `currency` and may carry `conversion?: { mainCurrency, rate, mainAmount, rateDate, source }` (unrounded; `source` = provider id, `manual` or `identity`) and `manualRate?: { mainCurrency, rate }`. An entry is converted only when `conversion.mainCurrency` equals the current main currency, otherwise pending. Every total sums `mainAmountOf()` (`src/lib/money.ts`: stored `mainAmount`, else the amount when already in the main currency, else `null` = pending, left out and counted); display uses `formatMoney` (2 decimals + code). Saving an entry in the main currency stores the identity conversion, anything else is stored pending; `updateExpense` keeps the conversion only while amount, currency and date are unchanged. The main currency and the rates switch live in the encrypted `syncedSettings` record (see Settings classification). `afterCommit` calls `requestEntryConversion()` for writes to `income` / `expenses_*` / `syncedSettings` (not for the converter's own `applyEntryConversions` / `convertBudgets`, which pass `fromConversion`); `prepareUnlockedVault` and `restoreBackup` call it too. localDb never imports `conversion.ts`.
- **Conversion engine** (`src/lib/conversion.ts`): `convertPending` (per-chunk writes under the lock, only `conversion` changes, never `updatedAt`; each date fetched once per run; missing rates leave entries pending; DecryptError propagates), `requestConversion` (one run at a time per tab, one shared follow-up), `whenConversionIdle`, `subscribeConversion`, `startAutoConversion` (`onConversionNeeded` + window `online`), `getConversionStatus`, `changeMainCurrency` (refuses with `MainCurrencyChangeError` `offline` / `rates-off` / `rates-unavailable` before writing; otherwise `localDb.convertBudgets(next, …, { setMainCurrency: true })` converts the live budgets at today's rate and stores the main currency in `syncedSettings` in one `setMany`, with revs, then every entry is recalculated). `ConversionRunner` in `__root.tsx` (always mounted next to `RecurringScheduler`) starts it and invalidates the data queries after each batch.
- **Exchange rates** (`src/lib/rates/`): `types.ts` (`RateProvider`, `RateTable`, `crossRate`, `RateUnavailableError`), `nbu.ts` (NBU statdirectory by date, `credentials: 'omit'`, no referrer, step back up to 7 dates, 3 tries with backoff on 429/5xx/network, at most 3 requests at once, no cache). **`src/lib/rates/index.ts` is the single swap point** (`rateProvider`); nothing else creates a provider. Tests must inject `fetchJson` / a provider or mock `@/lib/rates`, never call the real NBU.
- `ENABLE_SUPABASE_SYNC = false` at the top of `localDb.ts` is an old stub; real sync is `src/lib/sync/` behind `ENABLE_SYNC`.
- **Sync hooks in localDb:** `writeKeysMany` keeps the stored `meta:sync` fields and only replaces `localRev` (`syncMetaEntry(localRev)` does the same for `backup.ts`), and after a write that stamped revs calls the `onLocalChange` listeners (`notifyLocalChange`; incoming records, compaction and conversion never notify). `applyIncomingRecords(records, { preferIncomingOnTie })` takes the incoming record on an equal-time conflict (the server copy of a *stale* push). `compactTombstones(olderThan, { maxRev })` removes only tombstones with `rev <= maxRev`. `dedupeOccurrences(recurringIds)` tombstones legacy duplicate occurrences as a user write. `rekeyLiveData(newKey, { plain, syncPatch })` re-encrypts the live records under another DEK in one `setMany` (only `vault.joinCloudVault` uses it).

### Encryption flow — vault v2 (`src/lib/vault.ts`, primitives in `src/lib/crypto.ts`)

Spec: `docs/free-tier-spec.md` §4.

1. **Key hierarchy.** A random 256-bit **DEK** encrypts every record/chunk (AES-GCM). It is wrapped (AES-GCM) twice: by **KEK_pw** = PBKDF2-SHA256(password, 16-byte salt, **600,000** iterations) and by **KEK_rc** = HKDF-SHA256(recovery key, 16-byte salt, info `minima-recovery-kek-v2`). In use the DEK is imported **non-extractable**; raw DEK and recovery-key bytes are zeroed after use.
2. **Recovery key:** 160 bits, Crockford base32 in 5-char groups (`XXXXX-…-XX`, `encodeRecoveryKey` / `parseRecoveryKey` in `crypto.ts`). Input ignores case, spaces and dashes.
3. **Header:** `VaultHeaderV2` (`kdf`, `wrappedByPassword`, `recovery`, `verifier`, all base64) lives in the **same IndexedDB store as the data** under `meta:vault`, not in localStorage, and does not depend on the Supabase userId. The verifier (`AES-GCM(DEK, "minima-verify-v2")`) tells "Incorrect password" (unwrap fails) from "Vault damaged" (unwrap works, verifier fails).
4. **API:** `getVaultState()` → `'none' | 'v1' | 'v2' | 'orphaned'`; `createVault(pw)` → `{ recoveryKey }`; `unlockWithPassword(pw)` → `{ recoveryKey: string | null }` (non-null only after a v1 migration); `unlockWithRecoveryKey(key)`; `resetPasswordWithRecoveryKey(key, next)`; `changePassword(current, next)`; `regenerateRecoveryKey(pw)` → `{ recoveryKey }`; `lockVault()`; `clearLegacyKeys()`. Errors are `VaultError` with a `code` (`incorrect-password`, `incorrect-recovery-key`, `damaged`, `throttled`, `invalid-state`). Changing the password or the recovery key only re-wraps the DEK; data is never re-encrypted. Successful unlocks call `unlockLocalDb(dek)`.
5. **Brute-force delay:** `meta:settings` holds `failedUnlockAttempts` / `unlockBlockedUntil` (plaintext). Password and recovery-key checks share the counter; from the 5th failure in a row the delay is 5 s, doubling up to 5 min (`unlockDelayMs`). Success resets it.
6. **v1 → v2 migration:** a v1 store (`minima_key_verify_<userId>` + `minima_device_salt_<userId>` in localStorage, PBKDF2 200k) is migrated by `unlockWithPassword`: every data blob is decrypted in memory, gets `updatedAt` (`createdAt` for expenses/income), is re-encrypted with a new DEK, and all values plus `meta:vault` are written in **one** `setMany` transaction. A failure leaves v1 untouched. The UI then shows the new recovery key and, after the user confirms it, calls `clearLegacyKeys()` to remove `minima_device_salt_*`, `minima_key_verify_*` and `minima_offline_user`.

### Unlock gate (`src/routes/__root.tsx`)

No account is needed (spec §2.1). The root route has no auth requirement and never calls `getServerUser`.

- **Vault session** (`src/lib/vaultSession.ts`): a module-level store read with `useVaultSession()` (`useSyncExternalStore`). State is `{ phase, createRequested }`, phase `'checking' | 'none' | 'locked' | 'unlocked'`. On mount `RootDocument` maps `getVaultState()` through `phaseForVaultState` (`'none'` → `none`; `v1` / `v2` / `orphaned` → `locked`; a failed check → `locked`). The Header, the Landing page and `/` (Landing vs Dashboard) all branch on the phase.
- **Root `beforeLoad`:** on the client, a data route (`DATA_ROUTES`: `/analytics`, `/transactions`, `/income`, `/recurring`, `/settings` and sub-paths, `isDataRoute`) with no vault throws `redirect({ to: '/' })`. A failed state check lets it through (the gate shows recovery). Hydration doesn't re-run `beforeLoad`, so an effect in `RootDocument` also navigates home when the phase is `none` on a data route.
- **`computeGate({ mounted, phase, createRequested, pathname })`** decides the overlay: `showGate` when mounted and the phase is `locked`, or `none` after the user clicked "Start tracking" (`requestCreateVault()`, Landing hero or marketing Header). **Public routes** (`PUBLIC_ROUTES`: `/terms`, `/privacy` and sub-paths, `isPublicRoute`) are never covered by the gate, in any phase: they read no data and stay readable while locked. `showChildren` is false only for data routes after mount until the phase is `unlocked`, so their queries never run without a key; `/`, `/login`, `/auth/callback` and `/profile` keep rendering under the overlay.
- **`PasswordUnlockDialog`** (the gate) picks a screen from `getVaultState()` (components in `src/components/vault/`): `'none'` → `CreateVaultScreen` (password, then `RecoveryKeySaveStep`: Copy / Download .txt / Print, a checkbox and typing one full group: "Type group N of your key", N picked at random from 1–6 at mount by `pickConfirmationGroup`, never the 2-character tail, case and surrounding spaces ignored; a "Back" button calls `onCancelCreate` → `cancelCreateVault()`); `'v1'` / `'v2'` → `UnlockScreen` (v2 offers "Forgot password?" → `RecoverScreen`: recovery key, then a new password); after a v1 migration it shows the new recovery key before finishing. Confirming the key step (create, migration, Settings regenerate) calls `updateAppSettings({ recoveryKeyConfirmed: true })` (a failed write is logged and never blocks). For `'orphaned'` (data keys but no `meta:vault` and no v1 verifier), or if the state check fails, it shows a recovery state with "Restore from backup" (`unlock-recovery-restore` → `RestoreBackupDialog forceReplace`; on success a toast and `onUnlocked({ isNewVault: false })`) or "Erase local data and start fresh", which requires typing `DELETE`. `onUnlocked({ isNewVault })` calls `prepareUnlockedVault({ isNewVault })` (a DecryptError goes to `reportDataProblem`), sets the phase to `unlocked` and invalidates React Query caches.
- **Lock:** `lockApp(queryClient, { broadcast? })` clears the key (`lockVault()`), calls `queryClient.clear()`, moves `unlocked` to `locked` (never `none` to `locked`) and, unless `broadcast: false`, posts `{ type: 'lock' }`. A manual lock (Header `LockButton`, Settings → Security "Lock now") broadcasts, so it locks every tab. It never deletes data.
- **Auto-lock** (`src/lib/autoLock.ts`, `startAutoLock(minutes, onLock, doc?)`): `pointerdown` / `pointermove` / `keydown` count as activity; on becoming visible the elapsed time is checked directly, so hidden-tab time counts even when timers were throttled. The timeout (`Off`, 1, 5, 15 (default), 60 min) is in Settings → Security and stored in `meta:settings`. Auto-lock is **per tab**: `__root.tsx` calls `startTabAutoLock(minutes, queryClient)` (`vaultSession.ts`), which locks with `{ broadcast: false }`, so an idle tab never locks a tab that is in use.
- **Cross-tab:** `connectOtherTabs(queryClient)` listens for `lock` (lock this tab, no re-broadcast) and `wiped` (lock, then `reloadToHome()`; still affects every tab) on the sync channel.
- **Remove data from this device** (`RemoveDataDialog`, Settings → Data → Danger zone): confirms with the vault password (`verifyPassword`, no unlock, counts toward the brute-force delay) and offers "Download backup first". `wipeLocalData()` (`src/lib/localWipe.ts`) locks, clears the IDB store, removes every `minima_*` localStorage key, posts `wiped` and requests `indexedDB.deleteDatabase('minima-local')` (not awaited); callers then `reloadToHome()` (`location.replace('/')`). The "I've lost both" link in `RecoverScreen` opens the same dialog with typed `DELETE` and no backup.
- **Accounts (optional):** `ENABLE_ACCOUNTS` (`src/lib/featureFlags.ts`, `VITE_ENABLE_ACCOUNTS === 'true'`, default off) or an existing local Supabase session (`getAccountSession()` in `src/lib/accountSession.ts`, `auth.getSession()` in the browser) makes `useAccountsVisible()` true: Header "Sign in" and Profile link, Settings → Account (`AccountTab`). Signed out: the "Account (optional)" card (`account-optional-card`) with "Sign in with Google" → `/login?redirect=/settings?tab=account` and the Terms / Privacy links. Signed in: email, Sign out, Delete account, the legal links, and the Plan card (`account-plan-card`, fed by `useSyncStatus()`: loading / offline / error with Retry / ready with Beta, "included" or "not included"; no sync controls). `signOutAccount()` only ends the Supabase session; local data stays. `DeleteAccountDialog` keeps local data unless "Also remove data from this device" is ticked; deleting the account also deletes the encrypted cloud data (the `auth.users` delete cascades). `/login` validates `?redirect=` and the auth callback redirects with `redirect({ href })`, so a redirect keeps its own query string (same-origin paths only).
- **Terms and Privacy** (`/terms`, `/privacy`): public, server-rendered pages in both languages. The texts are typed content in `src/content/legal/{en,uk}.ts` (not the UI catalog; same section ids in both), rendered by `LegalDocument` (`src/components/legal/`); `src/lib/legal.ts` holds the types, the paths, `LEGAL_LAST_UPDATED` and the TODO operator constants. `LegalLinks` (Terms · Privacy) sits in the landing footer, under the legal pages and in Settings → Account; `/login` links both in its agreement sentence.
- **Durability (§6.1):** `CreateVaultScreen` calls `requestPersistentStorage()` after `createVault`; an unlock of an existing vault calls `ensurePersistentStorage()` (`src/lib/storagePersistence.ts`, records `persistRequestedAt`). Settings → Data shows `StorageStatusCard` (Protected / Best-effort, usage). On iOS Safari outside the Home Screen the Dashboard shows a one-time `InstallHintCard` (`src/lib/installHint.ts`; dismissal stored in `meta:settings`).

Settings tabs (Sync: see Sync engine; only with `ENABLE_SYNC` and visible accounts): General (Main currency with a confirm dialog, "Fetch exchange rates from the National Bank of Ukraine" switch, conversion status; the default tab) · Categories (Expense categories, Income categories) · Budget (limits always in the main currency) · Security (Change password, Generate new recovery key, Auto-lock, Lock now) · Data (Backup (.minima): download, restore, reminder frequency · Export CSV (.zip) · Import CSV · Storage status · Danger zone) · Account (only when accounts are visible).

### Cloud (`src/lib/cloud/`, spec §18)

The server side of encrypted sync (`supabase/migrations/20261023000000_sync_server.sql`, docs/db.md §8). The engine that uses it is in `src/lib/sync/` (see Sync engine).

- **Module map:** `types.ts` (record format, constants, snake_case wire types, `SERVER_ERROR_CODES`), `recordCrypto.ts` (pure: `deriveSyncKeys`, `recordKeyFor`, `encryptSyncRecord`, `decryptSyncRecord`, `SyncRecordError` with `decrypt-failed` / `unsupported-version` / `invalid-record`; never imports `vault.ts`), `api.ts` (`createCloudApi(rpc?)`: one method per SQL function with the SQL argument names, zod-validated results, every failure a `CloudError` with a server code or `network` / `unknown`; the default rpc builds the browser Supabase client lazily), `deviceId.ts` (`getDeviceId()` in localStorage `minima_device_id`, `defaultDeviceLabel()` "Chrome on Android"), `entitlements.ts` (the gate).
- **Record format (enc_v 1):** `record_key` = base64url (no padding) of HMAC-SHA256(K_index, `${type}:${id}`); `ciphertext` = base64 AES-GCM(K_data, 12-byte iv, JSON of the full `SyncRecord`) with `record_key` as additional data; `updated_at_ms` is the only clear-text value. K_index / K_data = HKDF-SHA256(DEK bytes, empty salt, info `minima-sync-index-v1` / `minima-sync-data-v1`), non-extractable.
- **`getSyncKeys()`** (`vault.ts`): `importDek` also imports the DEK bytes as non-extractable HKDF material into a WeakMap keyed by the in-use DEK, so every unlock path (create, v1 migration, unlocks, `openHeaderWithSecret`) has it; `getSyncKeys()` returns the memoised keys for `getLocalDbKey()` and rejects `VaultError('invalid-state')` while locked. The DEK is never exported and the header format is unchanged.
- **Permissions:** **`has_feature` in SQL is the only place permissions are decided** (`effective_plan()`: a valid non-`free` entitlement, else `beta` while `app_config.sync_free_for_all` is true, else `free`; limits live only in `plans.features`). **The client gate is `entitlements.ts`** (`hasFeature(status, 'sync')` reads `status.limits`, `useSyncStatus()`, `<FeatureGate feature fallback>`). **Never call a sync function without the gate, and never compare `plan_id`** (display names come from i18n by plan id; `granted_by` tells beta from paid). A guard test (`src/lib/cloud/guards.test.ts`) enforces this.
- **Who calls the api:** `useSyncStatus()` calls `getSyncStatus` (query `['sync-status']`, only when signed in and online, `staleTime` 5 min, `retry: false`, removed when the session goes away). Every other function is called only by `src/lib/sync/engine.ts` and `src/lib/sync/actions.ts`; `createCloudApi()` is called only in `api.ts`, `entitlements.ts` and `sync/runtime.ts` (guard test).

### Sync engine (`src/lib/sync/`, spec §19)

Behind `ENABLE_SYNC` (`src/lib/featureFlags.ts`, `VITE_ENABLE_SYNC === 'true'`, default off) **and** visible accounts (`useSyncAvailable()`). With the flag off no sync module does any work: `SyncRunner`, `SyncIndicator` and `SyncAvailable` render nothing / the fallback without calling a hook, `useSyncState()` returns `OFF_SYNC_STATE`, and the runtime is never built.

- **Module map:** `types.ts` (types only), `syncMeta.ts` (`parseSyncMeta`, `isSyncOn`, `readSyncMeta`, `updateSyncMeta`, `clearSyncFields`: the `meta:sync` fields under the `meta:sync` write lock; `localRev` is never changed there), `engine.ts` (`createSyncEngine(deps)`: the cycle, triggers, lock, backoff, state store), `actions.ts` (`createSyncActions(deps)`: turn on/off, link, restore, delete cloud data, devices, header changes; `SyncActionError`), `ports.ts` (the real localDb / vault / syncMeta / deviceId ports), `runtime.ts` (`getSyncRuntime()`: built lazily on first call, the only production `createCloudApi()` besides entitlements), `react.ts` (`useSyncState`, `useSyncAvailable`), `restoreRequest.ts` (`?restore=sync`). UI: `SyncRunner` (root: starts the engine while unlocked and signed in, stops it otherwise; password-changed toast; data problems; invalidates queries after a cycle), `SyncIndicator` (header), `settings/SyncTab`, `SyncDevicesList`, `SyncLinkDialog`, `DeleteCloudDataDialog`, `vault/SyncRestoreScreen`. **No work at import time** in any sync module: many tests mock `@/lib/vault` / `@/lib/localDb` partially.
- **The cycle:** preconditions (sync on, unlocked, signed in as `meta.userId`, online) → a fresh `getSyncStatus` + `hasFeature` → header (push a pending change with the expected `header_rev`, one retry after `header_conflict` when the cloud header wraps the same DEK; else adopt a newer cloud header with `adoptHeaderIfSameDek`) → pull every page from `pullCursor` (cursor saved per page; undecryptable rows skipped and counted into `lastError`) → `dedupeOccurrences` for the pulled recurring ids → push `listChangedRecords(pushedRev)` in `planPushBatches` (≤ 500 records, ≤ 1 MB), *stale* results applied with `preferIncomingOnTie` (the server wins exact ties), `pushedRev = snapshot.maxRev` only after every batch → `compactTombstones(now − 90 days, { maxRev })` → `lastSyncAt`. A checkpoint before every request ends the cycle when the vault was locked or `stop()` was called. `runCycle` never rejects; errors map through `statusForCloudError` (network / unknown retry with 5 s doubling to 5 min).
- **Triggers and the lock:** `start()` runs an `unlock` cycle, then local changes (debounced 2 s via `onLocalChange`), `online`, `visibilitychange` (visible only) and a 60 s interval (visible only); "Sync now" runs at once. One cycle at a time across tabs: `navigator.locks` `minima-sync` with `ifAvailable` (held → skipped, no call); in-tab, a second request during a cycle runs once afterwards.
- **Never push without the gate.** Every call that moves data or keys (`registerDevice`, `createVault`, `getVault`, `updateVaultHeader`, `pushRecords`, `pullRecords`) is preceded in the same flow by a fresh `api.getSyncStatus()` and `hasFeature(status, 'sync')` (engine: every cycle; actions: `requireSync()`). Deleting cloud data, listing / renaming / removing devices and turning sync off are not gated. `src/lib/cloud/guards.test.ts` enforces who may import and call the api. Sync code logs at most an error name, never records, keys, headers or ciphertext (no `console.log/info/debug` in `src/lib/sync/`).
- **meta:sync rules:** user writes keep the sync fields; only the engine and the actions write them. `pushedRev = -1` = the full snapshot is still to be pushed. Turning sync off clears the fields and keeps `localRev`; "Remove data" clears the store with them; sign-out keeps them.
- **Linking:** turn on → `register_device` (a removed device gets a new id via `resetDeviceId`) → `get_vault`: none → `create_vault` + full snapshot; same `vault_id` → link; other → `SyncLinkDialog` ("Join and keep": `vault.joinCloudVault` → `localDb.rekeyLiveData` in one transaction, then a cycle; "Replace": typed `DELETE`, `delete_cloud_data`, `create_vault`, full snapshot). Fresh device: `CreateVaultScreen` → `SyncRestoreScreen` → `actions.restoreFromCloud` (`vault.adoptCloudVault`, device registration, a full pull), then the normal `onUnlocked({ isNewVault: false })`. Header changes (`changePassword`, `regenerateRecoveryKey`, `resetPasswordWithRecoveryKey`) emit `subscribeHeaderChanges` → `headerPending` → the next cycle pushes it.
- **Simulating devices in tests** (`src/test/sync/`): each multi-device file mocks `idb-keyval` with `src/test/sync/memoryIdb.ts` (a per-handle in-memory store, `failNextSetMany` for injected failures) and builds devices with `createSimDevice()` (`src/test/sync/simDevice.ts`): `vi.resetModules()` then **dynamic** imports of localDb, vault, syncMeta, ports, engine, actions, backup and conversion, so every device has its own module singletons (DEK, store, locks, engine). Device ids, the signed-in user, online state, the lock manager, the timers (`SimClock.advance`) and window/document events are injected (jsdom's localStorage is shared). The api is `createCloudApi(rpc)` over the PGlite harness (`startDb()`, `ctx.rpcAs(userId)`, `setFreeForAll`), i.e. the real run 2 SQL functions and permission checks. Files run in the default jsdom environment; use `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime` to control `updatedAt`. A test that imports `@/lib/localDb` statically shares the first registry, so the helper imports everything dynamically. UI tests mock `@/lib/sync/react`, `@/lib/sync/runtime`, `@/lib/cloud/entitlements` (`useSyncStatus`) and `@/lib/featureFlags`.

### Spaces (`src/lib/spaces/`, spec §20)

Groundwork for a shared Family space next to the Personal space (no network code, no UI yet; `ENABLE_SPACES` / `VITE_ENABLE_SPACES`, default off, is not read by the UI).

- **Storage.** Personal keeps every key and the DEK. A Family space uses the same data keys prefixed `space:<spaceId>:` (plus `spaceInfo` and `memberProfiles`) and its own plaintext `space:<id>:meta:sync`. New personal data keys (encrypted with the DEK, synced by the personal engine): `identity` (the member's ECDH P-256 key pair) and `spaceKeys` (one entry per space with its random 256-bit space key, `keyVersion`, `previousKeys`, `name`, `role`). The keyring (`spaces/keyring.ts`) holds the imported space keys in memory; `wipeLocalDbKey` / `unlockLocalDb` clear it and it reloads from `spaceKeys` on the next Family access (`markKeyringStale()` after any `spaceKeys` write or a `spaceKeys` message from another tab).
- **The keyFor / cryptoFor rule.** Every storage key is built by `keyFor(spaceId, baseKey)` (`spaces/types.ts`; personal returns the base key) and every value is encrypted through `cryptoFor(spaceId)` (`localDb.ts`: the DEK for personal, the newest space key for a Family space, older versions tried for reads). **Never encrypt Family data with the DEK.** A Family space without its key (or any Family access while locked) raises `SpaceLockedError`; there is no fallback.
- **Making a function space-aware.** Implement it once in `localDb.ts` as `xIn(ctx, …)` against the space context (`readStore(ctx, key)`, `readChunk(ctx, chunk)`, `allExpenseChunkKeys(ctx)`, `withSpaceLock(ctx, keys, fn)`, `openRevCounter(ctx)`, `writeKeysMany(ctx, …)`, `afterCommit(ctx, …)`; base keys everywhere), export the personal wrapper with today's signature, and add the member to `SpaceDb` and `buildSpaceDb`. `spaceDb(spaceId)` returns the cached handle. Modules above `localDb` take an optional trailing `{ spaceId }` (`SpaceOption`) and reach the data through `dbFor(spaceId)` (`spaces/spaceDb.ts`: the `localDb` module namespace for personal, so test mocks of top-level functions keep working). **Personal calls keep exactly today's arguments**: pass `...spaceArgs(spaceId)` / `withSpaceOption(options, spaceId)` (vitest's `toHaveBeenCalledWith` fails on a trailing `undefined`).
- **Revs and member fields per space.** A Family write bumps only its space's `localRev` and never notifies the personal sync engine or `lastDataChangeAt`. Family user writes stamp `createdBy` / `updatedBy` (and `paidBy` on expenses and income, default the creator) with `getCurrentMemberId()` (`spaces/member.ts`, the account's user id or null; absent when unknown); `updatedBy` follows the rev rule. Personal records never get these fields.
- **Sync API.** `listChangedRecords(spaceId, sinceRev)` / `applyIncomingRecords(spaceId, records, options?)`; the one-argument forms are personal. Personal accepts `identity` / `spaceKey` records, a Family space `spaceInfo` / `memberProfile`. The personal engine is unchanged and carries `identity` and `spaceKeys`; there is no Family stream yet.
- **Spaces API.** `ensureIdentityKeyPair()` / `getIdentityPublicKey()`, `listLocalSpaces()`, `createLocalSpace({ name, lang? })` (one setMany), `forgetLocalSpace(id)` (tombstones the key entry, deletes `space:<id>:*`), `getSpaceInfo`, `getMemberProfiles`, `upsertMemberProfile`; `getActiveSpaceId()` / `setActiveSpaceId()` (`spaces/activeSpace.ts`, localStorage `minima_active_space`, unknown → personal).
- **Background work** covers every held space while personal is shown: `prepareUnlockedVault`, `RecurringScheduler` and the conversion background run iterate `listHeldSpaceIds()` (a mocked `localDb` registers no keyring loader, so it is `[]`).
- **React.** `__root.tsx` mounts `<SpaceProvider>` (always personal for now). Data components use `const spaceId = useActiveSpace()` and `const db = useSpaceDb()`, call `db.fn(...)` at call time (**never destructure the handle**: a test mock may not define every member) and key their queries with `spaceQueryKey(spaceId, base, ...rest)` = `[base, spaceId, ...rest]`. Invalidations stay base prefixes (`['expenses']`), which cover every space. A `changed` message carries `spaceId` only for a Family space.

### Backup & restore (`src/lib/backup.ts`, spec §7)

- **Format:** `MinimaBackupV1` (`format: 'minima-backup'`, `version: 1`, `createdAt`, `appVersion`, a snapshot of the vault header without `v`/`createdAt`, `payload: { enc, iv, ct }`, optional `skipped`). The payload is `JSON(BackupPayload)` (raw records with ids and full timestamps, plus `autoLockMinutes` / `backupReminderDays` / `mainCurrency` / `fetchExchangeRates` from `syncedSettings`; replace writes valid currency settings into `syncedSettings`, merge keeps the local record; records keep `conversion` / `manualRate` and `deletedAt`, never `rev`), gzipped with `CompressionStream` when available (`enc: 'gzip+aes-gcm'`, else `'aes-gcm'`) and encrypted with the DEK. Because the header is a snapshot, a backup opens with the password that was current when it was made, or the recovery key (unless regenerated since).
- **API:** `createBackup({ allowPartial })` reads the raw store directly; without `allowPartial` an unreadable key throws `DecryptError`, with it the key goes into `skipped` (partial backup, "Back up readable data" on the Data problem screen). `serializeBackup` / `parseBackupFile` (validates format, version, header and payload fields), `backupFileName()` (`minima-backup-YYYY-MM-DD.minima`), `defaultRestoreMode()` (`replace` when there are no live expenses, income, budgets or recurring items; `syncedSettings` doesn't count), `restoreBackup(file, secret, mode)` → `RestoreSummary`, `formatRestoreSummary`, `downloadBackup({ partial })`. Errors are `BackupError` with a `code` (`invalid-file`, `unsupported-version`, `wrong-secret`, `damaged`, `invalid-state`).
- **Opening a backup:** `openHeaderWithSecret(header, secret)` in `vault.ts` unwraps the DEK of any header with a password or a recovery key (`null` for a wrong secret, `VaultError('damaged')` when the verifier fails). It never touches the local brute-force counter. `getVaultHeader()` returns the local header.
- **Income categories in backups:** the payload carries `incomeCategories` (additive, `schemaVersion` stays 1, `RestoreSummary.incomeCategories`). A payload without it, or with income records that only have `source`, is converted with `convertIncomeSources` before planning (backup `updatedAt` kept; merge reuses local income categories by name; a replace without `incomeCategories` adds the defaults). Replace and merge treat `incomeCategories` like `categories`. After a replace restore, `ensureIncomeCategories()` runs as a safety net; a merge writes only the records that changed (one `setMany`, one rev per written record), and a device still without income categories gets them at the next unlock.
- **Recurring items in backups:** the payload carries `recurring` (additive, `schemaVersion` stays 1, `RestoreSummary` unchanged: changes count in added / updated / conflicts). Replace writes the list (`[]` when absent); merge upserts by id, newer `updatedAt` wins. A non-empty `recurring` makes `defaultRestoreMode()` return `merge`. A restore never generates records; the next `processDueRecurring` does, and the idempotency key prevents duplicates.
- **Restore:** nothing is written until the payload has decrypted and validated. Records are re-encrypted with the local DEK and everything (data keys, `meta:settings`, plus `meta:vault` on a fresh device) is written in **one** `setMany` transaction. Every record written gets a fresh rev, with `meta:sync` in the same `setMany`. **Replace:** the live data becomes exactly the backup; every live local record absent from the backup is kept as a tombstone (`deletedAt = updatedAt = now`, an expense in the chunk of its `createdAt`), local tombstones stay as they are, keys left with nothing become an encrypted `[]`; `syncedSettings` is written from the backup's valid values (else the local ones) and the legacy fields leave `meta:settings`; an undecryptable local blob is first copied to `quarantine:<key>:<ISO>` in the same transaction; `autoLockMinutes` / `backupReminderDays` are restored. **Merge:** upsert by `id` with `mergeRecord`: a strictly newer backup record wins (so a newer tombstone deletes); an equal timestamp with different content counts as a conflict and is decided by `sameTimeWinner` (tombstone, then the larger canonical JSON; written when the backup wins, counted in the collection count but not in added / updated); local-only records stay, expenses are regrouped into month chunks; a merge that writes no record writes nothing. **Fresh device** (`getVaultState() === 'none'`): the backup's header becomes `meta:vault`, mode is forced to replace and `unlockLocalDb(backupDek)` runs after the commit. **Orphaned device** (`'orphaned'`): restored the same way (header adopted, replace forced, unlocked after the commit), and every existing data value is copied unchanged to `quarantine:<key>:<ISO>` in the same `setMany` while its key gets the backup's records or an encrypted `[]`; nothing is deleted, and a failed commit leaves the store byte-identical. An adopted restore removes `recoveryKeyConfirmed` from `meta:settings` (the key belongs to the backup). Only locked and v1 devices are rejected. `lastBackupAt` is never taken from the file.
- **Spaces in backups** (spec §20): the payload also carries `identity`, `spaceKeys` and `spaces` (one `SpaceBackupPayload` per held Family space, read with its space key), each only when non-empty, so a store without spaces backs up exactly as before. A restore never replaces an existing local identity, merges `spaceKeys` in both modes (a replace never empties or tombstones them), restores a backed-up space (personal rules per space, its own revs and space key) only when the merged space keys hold a live key for it, otherwise lists it in `RestoreSummary.skippedSpaces` (`restoredSpaces` for the others; both only when non-empty), and leaves local spaces absent from the backup alone. `defaultRestoreMode` ignores the key material and every Family key.
- **Saving files:** `saveFile(blob, filename, { share })` (`src/lib/fileDownload.ts`) uses `navigator.share({ files })` when asked and supported (`'cancelled'` on `AbortError`), otherwise one anchor download, revoking the object URL after `OBJECT_URL_REVOKE_DELAY_MS` (10 s). `downloadBackup` shares; `lastBackupAt` is recorded only after `saveFile` resolves `'saved'`.
- **UI:** Settings → Data backup card (`backup-download-btn`, `backup-restore-btn` → `RestoreBackupDialog`, `backup-reminder-select`), the landing page "Restore from backup" (`RestoreBackupDialog freshDevice`, then the phase becomes `unlocked`), RemoveDataDialog "Download backup first", DataProblemScreen "Back up readable data" (`DataProblemGate` → `downloadBackup({ partial: true })`) and "Restore from backup" (`data-problem-restore`, replace only; `DataProblemGate` resets the queries, clears the problem and toasts), and the orphaned recovery screen in `PasswordUnlockDialog`. `RestoreBackupDialog forceReplace` (both recovery entry points) hides the mode select, skips `defaultRestoreMode` and shows a "will be replaced" note.

### Backup reminders (`src/lib/backupReminder.ts`, spec §6.2)

`meta:settings` also holds `backupReminderDays` (7 / 14 (default) / 30 / 0 = off), `lastBackupAt`, `lastDataChangeAt` and `backupReminderSnoozedUntil`; `getBackupSettings()` never throws and `updateBackupSettings` merges. The Dashboard `BackupReminderBanner` (query key `['backup-reminder']`, `getBackupReminderStatus()`) shows when reminders are on, data changed after the last backup (or there is none), the frequency has elapsed, the vault has ≥ 10 records and no snooze is active. "Later" snoozes for 3 days.

### CSV (`src/lib/localImport.ts`, `src/lib/localExport.ts`, spec §8)

CSV is for spreadsheets, not a backup ("Readable by spreadsheets · not encrypted · not a full backup"). Export is one `minima-csv-YYYY-MM-DD.zip` built with `fflate` (`buildCsvFiles`, `buildCsvZip`, `exportAllLocalData`). Import uses a quote-aware state-machine `parseCSV` (quoted commas, newlines and `""`, CRLF, BOM) with `,` / `;` detection (`detectDelimiter`) and `parseAmount` (decimal comma, space/NBSP thousands). Expenses and income skip rows whose fingerprint (`local date|amount|currency|category-or-source|description`) matches an existing record and report them as `duplicates` / `duplicateRows`; "Import them anyway" re-imports just those rows with `{ allowDuplicates: true, rows }`. Rows inside one file are not checked against each other. `expenses.csv` / `income.csv` end with `main_amount` (unrounded, empty when pending) and `main_currency`, which import ignores; `income.csv` starts `date,source,amount,currency,description`; the `source` column holds the income category name (legacy `source` text as a fallback on export). Import looks the name up in income categories ignoring case; an unknown name creates that income category (only for valid, non-duplicate rows) and `ImportResult.createdCategories` reports how many ("N new income categories created" in Settings → Data). `categories.csv` stays expense-only.

### PWA / Service Worker

Spec §6.3. Config is the `VitePWA` block in `vite.config.ts`; shared constants live in `scripts/precacheCheck.ts`.

- **Full precache:** workbox globs `.vercel/output/static` (`STATIC_OUTPUT_DIR`) for `js, css, woff, woff2, html, ico, png, svg, json`, i.e. every client chunk (including all route chunks), CSS, fonts, icons and `manifest.json`. `sw.js`, `workbox-*.js` and `_shell.html` are ignored by the glob. `maximumFileSizeToCacheInBytes` is 5 MiB.
- **App shell:** `tanstackStart({ spa: { enabled: command === 'build' } })` prerenders `/_shell.html` (`APP_SHELL_URL`, root route only) at build time; it is off in dev. The prerender runs after `generateSW`, so the shell is added through `additionalManifestEntries` with a per-build revision. Runtime SSR is unchanged (`TSS_SHELL` is unset on Vercel), and no other page is prerendered (never pass `prerender: { enabled: true }`, it would shadow SSR with static `index.html` files).
- **Navigations:** `NetworkOnly` with `precacheFallback` to `/_shell.html`, so online pages are SSR and offline navigations to any data route boot from the shell. There is no navigation runtime cache and no expiry anywhere: cached SSR HTML would outlive a deploy and reference chunks the new precache removed. `navigateFallback` stays `null`.
- **Bridge:** `vite-plugin-pwa` writes `sw.js` + `workbox-*.js` into `dist/`; `copySWPlugin` copies them into `.vercel/output/static/`, where Nitro/Vercel serves static files. `generateSW` runs once per environment (client, ssr, nitro) and the last copy wins.
- **Check:** `npm run test:precache` runs `vite build`, then `scripts/precacheCheck.test.ts` with `PRECACHE_BUILD_CHECK=1` (that block is skipped in plain `npm test`). It asserts every `assets/*.{js,css,woff,woff2}` file, the shell and the manifest icons are precached, and that `sw.js` has no expiry.
- **Shortcut:** `public/manifest.json` has one `shortcuts` entry, "Add expense" → `/transactions?add=expense` (icon `logo192.png`, already a precached manifest icon); offline it boots from the shell fallback like any navigation.
- **Online only:** `/profile`, `/login` and `/auth/callback` need the network (Supabase / server functions).
- The SW is registered manually in `RootDocument`'s `useEffect` (`/sw.js`).

### Languages (i18n)

The UI is Ukrainian + English, with a custom typed catalog and no i18n library (`src/i18n/`, spec §16).

- **Catalog.** `src/i18n/messages/en.ts` is the source (`as const`, grouped by area: `common`, `nav`, `landing`, `vault`, `dashboard`, `transactions`, `drawer`, `income`, `recurring`, `analytics`, `settings`, `backup`, `errors`, `toasts`, …). `uk.ts` is typed `LocalizedMessages`, so a missing or extra key is a type error. Leaves are strings with `{name}` placeholders; a plural node is `{ one, other }` in English and `{ one, few, many, other }` in Ukrainian.
- **Adding a string.** Add the key to `en.ts`, the same key to `uk.ts` (glossary and style: `docs/i18n/glossary.md`), use it, then run `npm run i18n:review` to regenerate `docs/i18n/uk-review.md` (a test compares it with the catalog). Components call `const { t, plural } = useT()` (`@/i18n`); every component that renders text or formatted values calls `useT()` so it re-renders on a language switch. Non-React code uses `t()` / `plural()` from `src/i18n/core.ts`. Keys are typed: an unknown key fails `tsc`.
- **Language state.** `getLang()` / `setLang(lang, { persist? })` / `subscribeLang` in `core.ts` (initially `'en'`). `setLang` also sets `<html lang>` and, unless `persist: false`, writes localStorage + the `minima_lang` cookie (`src/i18n/resolve.ts`). Resolution: stored choice, else `uk` for any `uk*` browser language, else `en`. The root route loader (`getRequestLang`, `src/i18n/server.ts`) reads the cookie, then `Accept-Language`, so SSR renders the right language; it returns `null` for the prerendered shell, where `I18nProvider` resolves the language in a layout effect before paint (`<body>` hidden meanwhile). "Remove data" clears the cookie too.
- **Formatting.** Only `src/i18n/format.ts` formats for display (`formatAmount`, `formatMoney`, `formatShortMoney`, `formatRate`, `formatNumber`, `formatDay`, `formatMonth`, `formatShortMonth`, `formatFullDate`, `formatTime`); they follow the UI language, never the device locale. Ukrainian shows UAH as "грн" and keeps USD / EUR codes (`currencyLabel`). `src/lib/money.ts` re-exports the money helpers. Machine formats (`YYYY-MM-DD` storage keys, CSV, URLs, file names) stay on dayjs. Ukrainian digit groups use the no-break space ICU emits; tests match `\s`.
- **Errors.** Lib code throws errors with a stable `code` (`VaultError`, `BackupError` (+ `reason: 'compression'`), `MainCurrencyChangeError`, `AppError` in `src/lib/appErrors.ts`, `DecryptError`) and keeps today's English `message`. The UI shows `errorMessage(err)` (`src/i18n/errors.ts`, duck-typed on `name` + `code`). Zod messages in `src/lib/schemas.ts` are catalog keys (`errors.validation.*`); show them with `validationMessage()`. CSV import row problems are `ImportResult.rowErrors` (`{ row, code, value }`). Lib text helpers (`pendingLabel`, `recurringCreatedMessage`, `formatRestoreSummary`, `backupReminderText`, `bestEffortHint`, `storageKeyLabel`, `incomeSourceLabel`, `formatBytes`, `describeFrequency`) read the current language through `core.ts`; lib never imports React.
- **Default categories.** `prepareUnlockedVault({ isNewVault, lang })` writes the defaults of `lang` (`src/lib/defaultCategories.ts`) for a new vault; existing categories are never renamed.
- **Guard test.** `scripts/untranslatedText.test.ts` (TypeScript compiler API, `scripts/untranslatedText.ts`) fails on JSX text with letters, string literals in `aria-label` / `placeholder` / `title` / `alt`, and string literals passed to `toast(...)`, in `src/**/*.tsx` except tests and `src/components/ui`. Allowed: "MinimaSpend", currency codes, emoji, digits and punctuation.
- **Tests.** Pin the language in every test that renders text or formats values (`setLang('en', { persist: false })` in `beforeEach`, or `<I18nProvider initialLang="uk">`), and build expected amounts and dates with the format helpers and an explicit language.

### Key derivation for `localDb.ts` writes

Any function that writes to IDB requires `_key` to be non-null. If you add a new write operation and tests fail with "LocalDb not initialized", the DB hasn't been unlocked yet in that code path.
